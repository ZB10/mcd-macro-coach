# 麦门营养师 · mcd-macro-coach

> 减脂期站在麦当劳柜台前，你其实只想知道两件事：**这顿吃多少卡**、**在预算里怎么点最划算**。
> 这个 Skill 直接给出答案，并且答案能直接下单。

一个基于麦当劳 MCP 的营养配餐求解器。输入身体数据和预算，输出一份**营养达标、价格真实、可直接下单**的餐品组合。

不是"建议你少吃炸物"这种废话——它给你具体到 `productCode` 的清单。

---

## 它解决什么问题

健身的人想吃麦当劳，卡在三件事上：

1. **算不出来。** 麦当劳公开了 158 条餐品营养数据，但那是按**单品**列的。你点的是「猪柳蛋麦满分套餐」，它由汉堡 + 薯饼 + 咖啡组成，营养得自己加。菜单上大半是套餐，等于大半算不出来。
2. **配不出来。** 知道了目标（比如这餐 450 大卡、35g 蛋白），在 70 多件商品里凑出最接近的组合，是个人肉背包问题。
3. **价格会变。** 菜单上写着 13.20 元的套餐，结账时是 22.00 元——因为那是"随单购早餐卡"价，前提是你先买张卡。按 13.20 做预算，到柜台就尴尬了。

这个项目把这三件事都做了：**拆解套餐、求解组合、核对真实价格**。

几处刻意的设计：

- **套餐展开到子项**。不告诉你这 434 大卡由什么组成，就等于没算。
- **替换明着说**。套餐默认饮料「鲜萃冰咖」没有公开营养数据，程序换成了同价位的「小杯鲜萃咖啡」——但会明确告诉你换了什么、差价多少，由你决定要不要接受。
- **钠超标不遮掩**。麦当劳早餐普遍 700mg+ 钠，硬说"很健康"是不负责的。指出具体哪一件贡献最多，比笼统警告有用。
- **给出下单 code**。方案能直接喂给 `calculate-price` / `create-order`，不是纸上谈兵。

## 快速开始

### 前置条件

需要麦当劳 MCP Token。申请方式见 [麦当劳 MCP 使用指南](https://github.com/M-China/mcd-mcp-server)。

### 1. 配置 MCP

在 WorkBuddy 的【连接器】→【自定义连接器】→【配置 MCP】中填入：

```json
{
  "mcpServers": {
    "mcd-mcp": {
      "type": "streamablehttp",
      "url": "https://mcp.mcd.cn",
      "headers": {
        "Authorization": "Bearer YOUR_MCP_TOKEN"
      }
    }
  }
}
```

### 2. 抓取门店数据

```bash
export MCD_MCP_TOKEN="your-token"

python scripts/fetch_mcp.py --store 3500027 --out examples/store_3500027.json
```

会抓取菜单和所有套餐的拆解详情，落盘缓存。之后求解全部读本地文件，不再请求网络。

> 仓库里已内置 `examples/demo_store.json`（真实门店数据，保留 6 份套餐详情），**没申请到 Token 也能直接跳过这一步跑通全流程**。需要完整覆盖时再执行上面的命令。

### 3. 出方案

```bash
python scripts/cli.py plan --menu examples/demo_store.json \
    --weight 70 --height 175 --age 28 --sex male \
    --goal cut --meal breakfast --budget 30 --top 3
```

参数说明：

| 参数 | 说明 |
|---|---|
| `--goal` | `cut` 减脂 / `maintain` 维持 / `bulk` 增肌 |
| `--meal` | `breakfast` / `lunch` / `dinner` / `snack` |
| `--activity` | `sedentary` / `light` / `moderate` / `active` / `athlete` |
| `--with-card` | 已持有早餐卡，按随单购价计算 |
| `--require-drink` | 方案必须含饮品 |
| `--json` | 输出 JSON，便于程序消费 |

### 4. 检查数据覆盖率

```bash
python scripts/cli.py audit --menu examples/demo_store.json
```

会告诉你这个门店有多少餐品的营养能对上、哪些对不上。**先看这个再信方案**——覆盖率低说明这家店的菜单结构和你预期的不一样。

### 5. 跑测试

```bash
python -m unittest discover -s tests -v
```

零第三方依赖，Python 3.10+ 即可运行。

## 工作原理

```
query-meals ──────────► 菜单（productCode 索引，名称是营销名）
                              │
query-meal-detail ────► 套餐 rounds（还原成单品清单）
                              │
list-nutrition-foods ─► 营养表（中文品名索引）
                              │
                        名称对齐（本项目核心）
                              │
                        Meal（价格 + 营养 + 槽位）
                              │
                        TDEE → 单餐目标
                              │
                        组合求解（预算约束下最小化偏差）
                              │
                        方案 + 缺口分析 + 下单 code
```

### 三个关键决策

**1. 名称对齐：宁可返回空，也不猜**

菜单用 `productCode` 索引，营养表用中文品名索引，两套命名不同步：

| 菜单侧 | 营养侧 |
|---|---|
| `纯牛奶(盒装)` | `纯牛奶（盒装）` |
| `麦咖啡™热美式中杯` | `热美式中杯` |
| `可乐` | `可乐中杯` / `可乐大杯` / `可乐小杯` |

逐级降级匹配：精确 → 别名 → 去品牌前缀 → 补默认杯型 → 模糊。模糊匹配设了 0.90 阈值**加长度差 ≤2 的限制**，否则「优品豆浆」会被吃成「优品豆浆大杯」，热量差 51 大卡还看不出来。

配错比配不上更糟。所以查不到就返回 `None`，由上层标为"营养未知"。

**2. 套餐拆解：isDefault 和 quantity 会打架**

`query-meal-detail` 返回的 rounds 里，`isDefault`（推荐项）和 `quantity`（已选数量）可能互相矛盾。实测「猪柳蛋麦满分套餐」的饮料轮次：

- `大杯鲜萃咖啡`：isDefault=1，quantity=0
- `鲜萃冰咖`：isDefault=0，quantity=1

`quantity` 反映真实选择，`isDefault` 只是推荐。取值必须 quantity 优先。

**3. 价格：菜单价不一定是支付价**

`query-meals` 的 `currentPrice` 可能已包含「随单购早餐卡优惠」。实测「原味板烧鸡腿炒双蛋堡组合」currentPrice=13.20、originalPrice=22.00，而 `calculate-price` 算出来是 **22.00**——13.20 的前提是先买卡。

所以默认按原价计入预算，卡价单独展示。想按卡价算就加 `--with-card`。

## 数据准确性

不粉饰，实测数据如下（合肥新地购物中心餐厅，2026-10-20，**完整抓取 29 份套餐详情**；仓库内置的 `demo_store.json` 只保留 6 份，覆盖率会低一些）：

| 指标 | 数值 |
|---|---|
| 营养表条目 | 158 条 |
| 门店菜单餐品 | 78 件 |
| 营养可计算 | 48 件（**61.5%**） |
| 其中套餐 | 19 份（经拆解还原） |
| 无法计算 | 30 件 |

**剩下 39.5% 为什么算不出来？**

- 主餐本身没有公开营养数据：`芝芝火腿扒堡`、`吉士蛋麦满分`、`枫糖风味厚松饼猪柳堡` 等。营养表覆盖的是经典款，新品和区域限定常缺席。
- 冷热二义：`麦咖啡™奶铁` 可能是热奶铁也可能是冰奶铁，热量差一倍，不能猜。
- 规格缺失且无中杯：`优品豆浆` 只有大杯/小杯，没有默认值可套。

这些不会进入推荐，也不会被强行填一个数字。`audit` 命令会完整列出。

**价格验证**：抽样用 `calculate-price` 核对，与本地计算一致（差异来自随单购条件，已单独处理）。

## 目标用户

- **减脂/增肌的健身人群**：需要精确热量和蛋白，不想每天手算。
- **有预算约束的学生和上班族**：想在 20-30 元内吃到最划算的组合。
- **需要控钠的人**：想快速知道哪一件餐品是钠的主要来源。
- **做餐饮/健康类产品的开发者**：可以直接复用名称对齐和套餐拆解逻辑。

## 已知局限

- **单餐求解，不做全天规划**。目前只算一餐，跨餐的钠和热量分配还没做。
- **营养数据是静态快照**。麦当劳更新菜单后需重跑 `fetch_mcp.py`。
- **未接入优惠券**。`query-store-coupons` 已预留，组合优化时把券纳入能进一步压价。
- **未做特调**。加芝士、去酱会影响营养，当前按默认配置计算。
